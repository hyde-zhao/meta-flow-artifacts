## 用户画像

| 画像 ID | 用户 | 工作情境 | 想达成的结果 | 当前痛点 |
|---|---|---|---|---|
| P-RA-01 | 测试经理 | 现网事故恢复后，要在进度、风险和资源之间做取舍 | 知道哪些事故必须系统性复盘、谁负责、何时可向干系人说明风险已受控 | 事故“恢复”常被误解为问题“解决”，改进项无人跟踪 |
| P-RA-02 | 测试架构师 | 需要与开发、运维和测试团队共同解释一次事故 | 用证据解释问题为何发生、为何未被更早发现，并选择最经济的预防点 | 信息散乱、根因与触发器混淆，容易形成不可执行的结论 |
| P-RA-03 | 测试设计负责人 | 收到事故教训，需要决定如何补齐测试策略和用例 | 获得清晰、经过批准且可验收的漏测/边界场景输入 | 只有泛化的“补用例”要求，无法判断覆盖范围和优先级 |
| P-RA-04 | 质量负责人 | 需要判断 CA/PA 是否真正降低了复发风险 | 能审计行动项、验证证据、观察窗和未关闭风险 | 行动项完成即关闭，缺少有效性和复发证据 |
| P-RA-05 | 安全 / 合规负责人 | AI 分析涉及事件材料与改进建议 | 保证分析不会读取敏感资料、越权连接系统或把建议当成生产操作 | “只读分析”常被误解为可以访问日志、工单或生产设备 |

## 明确排除

- 不替代事故指挥、现场恢复、TAC 沟通或生产缓解。
- 不直接访问设备、日志、PCAP、工单、知识库或任何外部平台。
- 不读取凭据、秘密、会话或账号；不写生产配置、策略、工单或发布记录。
- 不把内部测试/预发布问题套入现网逆向分析模型。

## 使用场景列表

### UC-RA-01：测试经理决定是否为一次已恢复事故启动系统性预防

| 字段 | 内容 |
|---|---|
| **用户与目标** | 测试经理希望在事故刚恢复时判断是否需要投入团队复盘，以免把“服务恢复”误当成“风险消失”。 |
| **触发条件** | P1/P2 现网问题已恢复，测试经理收到影响摘要、恢复时间和证据保全状态。 |
| **用户输入** | 事件严重度、业务影响、恢复状态、已有证据摘要、最近变更和责任协作人。 |
| **用户旅程** | 测试经理查看“是否应启动”的理由 → 确认 P1 必做或对 P2 选择启动 → 指定测试架构师和预期截止时间 → 跟踪分析是否在 72 小时内启动。 |
| **用户获得的结果** | 明确的启动/不启动决定、责任人、时限和可向干系人解释的风险理由。 |
| **协作关系** | 测试架构师接手分析；质量负责人后续检查闭环。 |
| **失败体验 / 排除** | 事件未恢复、非现网、P3/P4 或证据未保全时，用户看到“不适用/需补充”而非伪造分析。 |

### UC-RA-07：测试架构师把现网问题单变成可信的分析输入与风险全景

| 字段 | 内容 |
|---|---|
| **用户与目标** | 测试架构师希望从受控的数据来源获得并保存现网问题单，既能追溯每条结论的来源，也能从一批问题中发现重复的测试风险和改进机会。 |
| **触发条件** | 测试经理要求查看指定时间段/产品的现网问题趋势，或测试架构师需要为已恢复问题建立分析候选池；仅在 ITR 读取与保存边界获批准后触发。 |
| **用户输入** | 产品、时间范围、分页范围以及用户提供的 ITR 请求；无凭据、无认证头和无写入参数。 |
| **用户旅程** | 架构师发起受控拉取 → 查看请求范围、响应数量和 schema/数据质量提示 → 保存带来源与时间的快照/规范化记录 → 选择单个问题或一组问题进入分析 → 审阅逐单结论与批量趋势总结。 |
| **用户获得的结果** | 可追溯、可去重的问题单分析输入；一份区分事实与假设的单问题单总结，以及可用于优先级决策的批量风险/趋势概览。 |
| **协作关系** | 测试经理用概览决定投入优先级；安全/合规负责人审查读取和保存边界；测试设计负责人消费经批准的改进输入。 |
| **失败体验 / 排除** | 接口不可用、响应 schema 不匹配、字段缺失、保存失败或数据分类未确认时，用户得到明确错误/缺口并保留已有快照，不覆盖历史数据或编造结论；不读取其他系统。 |

### UC-RA-08：测试架构师刷新问题单风险全景并解释本次变化

| 字段 | 内容 |
|---|---|
| **用户与目标** | 测试架构师希望在已有分析后重新获取 ITR 数据，识别新增问题单及状态、定位、解决信息变化，合并可靠数据并说明风险、趋势和改进措施相对上次发生了什么变化。 |
| **触发条件** | 已存在某产品/时间窗的摄取批次和分析报告，用户请求刷新或定期比较本期与上期/去年同期。 |
| **用户输入** | 新拉取批次、上次已保存版本、比较时间窗、质量/冲突策略和已批准或待处理的改进措施。 |
| **用户旅程** | 拉取增量 → 清洗并质量标记 → 按稳定 ID 检测新增/修改/未变化 → 保存版本与变更历史 → 合并规范化记录 → 仅重算受影响维度并刷新全量指标 → 输出差异报告和需要重新评估的措施。 |
| **用户获得的结果** | 可审计的新增、状态变化、定位/解决信息变化、同比/环比及改进措施变化列表；历史版本不被覆盖。 |
| **协作关系** | 测试经理依据差异决定优先级；质量负责人复核趋势与措施状态；测试设计负责人消费重新批准的改进输入。 |
| **失败体验 / 排除** | 无稳定 ID、冲突无法解决、数据质量不达标或比较窗口不足时，报告标记不可信/待人工决策，不合并、不刷新已批准结论。 |

### UC-RA-09：测试架构师治理已安装项目中的 ptm-tse 运行数据

| 字段 | 内容 |
|---|---|
| **用户与目标** | 测试架构师已在项目目录（例如 `/home/hyde/projects/ptm-tse/`）安装并验证 `ptm-tse`，希望持续治理已有 SQLite、WAL/SHM、原始快照、批次/分析元数据，使真实问题单数据不会因权限、保留或 support/data 混放而泄露或不可审计。 |
| **触发条件** | 首次摄取后、版本更新后、安装升级前，或安全/合规负责人要求核验本地问题单数据边界时。 |
| **用户输入** | 已安装项目根、运行数据清单、数据类别、保留策略、权限核验结果和数据 Owner 的清理授权（如有）。 |
| **用户旅程** | 架构师枚举运行数据 → 区分 runtime data 与可交付 support → 核验目录/文件权限和 git 排除 → 记录保留/清理状态 → 发现不合格项时阻断继续分析并生成修复清单 → 在数据 Owner 明确授权后执行受控修复或清理。 |
| **用户获得的结果** | 每项数据有类别、Owner、权限、保留状态和来源；SQLite、WAL/SHM、原始快照及分析/批次元数据受到一致保护，support 文件不再被误当运行数据或无来源复制。 |
| **协作关系** | 安全/合规负责人确认敏感数据规则；数据 Owner 决定保留与删除；测试架构师继续按 UC-RA-07/08 使用合格数据。 |
| **失败体验 / 排除** | 文件权限不合格、未分类数据、support 来源不明或无清理授权时，用户看到明确阻断/修复清单；不自动 chmod、删除、迁移真实数据，不重新实现已验证的项目级安装。 |

### UC-RA-02：测试架构师为团队建立可信的事故事实基础

| 字段 | 内容 |
|---|---|
| **用户与目标** | 测试架构师希望在跨团队讨论前建立共同事实，避免每个人依据片段日志或经验争论。 |
| **触发条件** | 测试经理已启动分析，或测试架构师主动接手一个合格事件。 |
| **用户输入** | 脱敏事件摘要、时间线、流量/策略/状态/资源/变更证据索引、已尝试缓解记录。 |
| **用户旅程** | 架构师查看证据完整度 → 将材料归入五条证据线 → 标出事实、假设和未知项 → 在不足时向责任人索要具体缺口。 |
| **用户获得的结果** | 一份可审计的事实基线；若不足三条有效证据线，则得到“不能下结论”的缺口清单。 |
| **协作关系** | 事件 Owner/运维补充摘要；安全负责人可审查敏感边界。 |
| **失败体验 / 排除** | 用户不能通过补充猜测绕过证据阈值；系统不代为连接日志、设备或工单。 |

### UC-RA-03：测试架构师向团队解释问题为什么发生且没有被更早拦住

| 字段 | 内容 |
|---|---|
| **用户与目标** | 测试架构师希望让团队理解“根因、引入点和流出点”之间的关系，从而选择成本最低的预防位置。 |
| **触发条件** | 事实基线已达到最低证据要求，跨团队评审准备开始。 |
| **用户输入** | 经分类的事实、假设、时间线、现有测试/发布/监控控制信息。 |
| **用户旅程** | 架构师梳理时间线 → 组织可能原因 → 验证假设 → 区分触发器和根因 → 回溯最早引入点 → 对各控制层为何失效达成共识。 |
| **用户获得的结果** | 经人工确认的根因、触发器、促成因素、引入点、流出路径和最近可拦截点。 |
| **协作关系** | 开发、运维、测试和质量代表可修正结论；人工 reviewer 决定确认。 |
| **失败体验 / 排除** | 证据不足或 reviewer 不同意时，结论保持为草案/待澄清，不能进入改进分发。 |

### UC-RA-04：测试设计负责人把事故教训变成可验证的测试改进

| 字段 | 内容 |
|---|---|
| **用户与目标** | 测试设计负责人希望收到明确的漏测模式和验收边界，以便把教训转成测试策略、用例或数据设计，而不是接收一句“补测试”。 |
| **触发条件** | 问题分析和 CA/PA 已由 reviewer 批准，改进输入目标为测试设计。 |
| **用户输入** | 已批准改进输入：来源 RA/问题单、漏测/边界描述、适用范围、验收标准、优先级、限制与批准引用。 |
| **用户旅程** | 负责人检查输入是否完整 → 判断其影响策略、场景或用例 → 形成自己的设计任务/反馈引用 → 把结果回链到原 RA。 |
| **用户获得的结果** | 有优先级、可验证、可追溯的测试改进工作，而非未经确认的建议。 |
| **协作关系** | 同类输入可分别由执行、自动化和质量负责人消费；ptm-tse 不直接修改其产物。 |
| **失败体验 / 排除** | 输入未批准、字段缺失或消费者不适用时，负责人看到待补充/不适用，不会被强制创建任务。 |

### UC-RA-05：质量负责人确认改进真正降低了复发风险

| 字段 | 内容 |
|---|---|
| **用户与目标** | 质量负责人希望在报告“关闭”前看到行动、验证和观察证据，避免完成率替代有效性。 |
| **触发条件** | CA/PA 已有 Owner、期限和实施反馈，或测试经理请求关闭 RA。 |
| **用户输入** | 行动状态、短期验证证据、横向排查结果、30 天观察数据、同类复发指标。 |
| **用户旅程** | 质量负责人检查每项关闭条件 → 判断短期修复是否有效 → 观察同类问题是否复发 → 允许关闭或要求保持开放。 |
| **用户获得的结果** | 可解释的关闭/不关闭决定，以及仍需承担的风险和后续行动。 |
| **协作关系** | 测试经理汇报进度；测试架构师解释技术证据；改进 Owner 补充验证。 |
| **失败体验 / 排除** | 观察窗不足、Owner 未完成或证据不充分时不能关闭；系统不伪造 30 天真实观察。 |

### UC-RA-06：安全/合规负责人防止分析越过数据与操作权限边界

| 字段 | 内容 |
|---|---|
| **用户与目标** | 安全/合规负责人希望团队能从事故学习，但不因此扩大 AI 对生产数据或操作系统的访问。 |
| **触发条件** | 分析输入包含敏感材料、凭据、外部系统访问要求，或有人要求直接执行修复。 |
| **用户输入** | 处理请求、数据来源声明、授权说明和事件分类。 |
| **用户旅程** | 负责人确认请求是否在授权范围 → 要求脱敏摘要或拒绝不安全路径 → 指向独立 runtime/security CR。 |
| **用户获得的结果** | 可审计的拒绝/降级记录；团队仍可用合规的摘要继续分析。 |
| **协作关系** | 测试架构师按限制重构输入；测试经理决定是否发起新授权流程。 |
| **失败体验 / 排除** | 不会静默读取凭据、日志、工单或生产设备；不会执行配置或修复。 |
