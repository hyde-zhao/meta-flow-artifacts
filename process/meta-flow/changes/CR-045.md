# CR-045 CR-aware route planning and N/A checkpoint semantics

## Change Description

This CR turns the CR-156 double-report diagnosis into an executable implementation plan for Meta Flow itself.

CR-156 was an existing-evidence process hygiene closeout: no new design, no new implementation and no new verification. It should have been routed as a compact closeout, but the workflow defaulted toward CP3-CP8 until manual review corrected the path. The root cause is not a total absence of gate profiles; the current code already has `docs-lite`, `process-lite`, `standard-lite`, `standard-code`, `architecture-major` and `runtime-high-risk`. The gap is that CR intake, route planning, state-router progression, CP result semantics and dispatch evidence are not connected by a single machine-enforced contract.

## Scope

In scope:

- Add executable route-plan policy logic so CP0 can derive an actual CR route from CR facts.
- Normalize `*-lite` stage notation into standard CP IDs plus `mode=lite`; CP result `checkpoint` remains `CP0` through `CP8`.
- Support checkpoint-level `decision=N/A` and keep it distinct from `WAIVED`.
- Make state-router consume `route_plan` instead of only the fixed CP0-CP8 phase table.
- Allow route-plan N/A checkpoints to be skipped without generating independent ceremonial result JSON files.
- Standardize `dispatch_not_required` / `inline-fallback` evidence for CRs that do not require subagent work.
- Add silent validation mode for low-token JSON/ledger checks.
- Add a later aggregate applicability schema for audit reconstruction without reintroducing N/A result-file noise.
- Add CR-156-style fixture coverage so existing-evidence closeout routing cannot regress.

Out of scope:

- Changing product requirements, use cases or Story boundaries.
- Authorizing runtime, credential, NAS, production, publish or trading actions.
- Deleting legacy CR files, Story files or historical ledgers.
- Replacing the whole CP0-CP8 model.
- Repository push / remote publication execution.

## Accepted Design Decisions

| Decision | Accepted Direction | Reason |
|---|---|---|
| Classification model | `cr_type` remains the primary category; `cr_kind` becomes deprecated compatibility; `cr_trait` contains route facts only | Avoids a third overlapping taxonomy |
| `cr_trait` shape | Use booleans / tri-state route facts, not `cr_trait.type` | Keeps route facts orthogonal to CR category |
| Lite stages | Normalize `CP2-lite` to `checkpoint=CP2`, `mode=lite` | Avoids polluting CP result IDs and `CHECKPOINT_RE` |
| Route precedence | `gate_profile` is the default maximum governance path; `route_plan` is the CP0-derived actual path | Prevents profiles from being bypassed while allowing safe pruning |
| N/A vs WAIVED | `N/A` means the CP is not applicable; `WAIVED` means applicable but explicitly skipped | Preserves audit semantics |
| N/A result files | N/A CPs do not generate independent result JSON after route-plan support lands | Eliminates ceremonial artifacts at the source |
| Aggregate schema | Aggregate applicability is a separate schema/checker, not a new `checkpoint=CP-AGGREGATE` in the main CP result schema | Keeps CP0-CP8 result contract stable |
| Validation derivation | `has_new_implementation=true` implies CP7 unless explicitly waived with risk acceptance | Prevents unverified implementation paths |

## Route-Plan Policy Contract

### Executable Policy Location

Create `meta_flow/policies/route_plan.py`.

Primary entry point:

```python
derive_route_plan(
    *,
    cr_type: str,
    cr_trait: dict,
    gate_profile: str,
    product_baseline_refresh_required: bool = False,
    impact_surface: list[str] | None = None,
    authz_policy_refs: list[str] | None = None,
) -> dict
```

Responsibilities:

- Normalize profile stages such as `CP2-lite` to structured stage objects.
- Derive CP applicability from `cr_type`, `cr_trait`, profile and product-baseline flags.
- Auto-derive verification requirements from implementation requirements.
- Emit warnings and blockers for contradictory traits.
- Return a deterministic route plan that state-router can consume.

CLI preview target:

```bash
meta-flow route plan --cr-type process --gate-profile process-lite --cr-trait cr_trait.json --project-root .
```

`gate_profiles.py` remains responsible for profile registry/classification. `route_plan.py` consumes profile output and CR facts to produce the actual route.

### CP0 Intake Sequence

The CP0 intake sequence must be deterministic:

1. User request enters Host Orchestrator.
2. Host Orchestrator proposes draft `cr_type` and `cr_trait`.
3. `classify_gate_profile()` proposes `gate_profile`.
4. `derive_route_plan()` produces draft `route_plan`.
5. CP0 result JSON records `cr_type`, `cr_trait`, `gate_profile` and `route_plan`.
6. CP0 PASS creates / updates the formal CR file and copies or references the route facts.
7. state-router reads the CP0 result route plan until the formal CR summary/index exists, then uses the summary/index route reference.

If CP2 changes scope/authz meaning, the workflow must create a route-plan amendment or amended CP0 result. It must not silently edit only CR frontmatter.

### Trait Fields

`cr_trait` fields:

```yaml
cr_trait:
  uses_existing_evidence_only: false
  has_new_design: false
  has_new_implementation: false
  has_new_verification: null
  requires_architecture_review: false
  requires_story_decomposition: false
  requires_subagent_dispatch: false
  verification_waiver_reason: ""
  existing_evidence_refs: []
  classification_reason: ""
```

`has_new_verification=null` means unspecified. `derive_route_plan()` derives it when implementation exists.

### CP Applicability Mapping

| Condition | CP impact |
|---|---|
| `uses_existing_evidence_only=true` | CP3/CP4/CP5/CP6/CP7 are N/A if no contradictory new design/implementation/verification flags exist |
| `has_new_design=true` | CP3 applies; CP4/CP5 apply only when Story/Feature decomposition or implementation design evidence is required |
| `requires_architecture_review=true` | CP3 applies in standard mode with human gate required |
| `requires_story_decomposition=true` | CP4 and CP5 apply; CP3 applies at least lite unless a confirmed design baseline already exists |
| `has_new_implementation=true` | CP6 applies; CP7 is derived as applicable unless explicitly waived |
| `has_new_verification=true` | CP7 applies |
| `has_new_implementation=true` and `has_new_verification=false` without waiver | CP0 BLOCKED |
| `has_new_implementation=true` and `has_new_verification=false` with waiver | CP7 is WAIVED, not N/A; waiver and risk acceptance are required |
| `requires_subagent_dispatch=false` | Dispatch mode may be `not-required` if all applicable downstream CPs are N/A or host-owned |
| Contradictory trait, for example existing evidence only plus new implementation | CP0 BLOCKED or trait must be corrected before route finalization |

### CP1 Applicability

CP1 is controlled by gate profile and product-baseline refresh, not ordinary `cr_trait` booleans.

Rules:

- `architecture-major` and `runtime-high-risk` require CP1.
- `product_baseline_refresh_required=true` requires CP1, even if the initial profile is lighter.
- `cr_type=product-scope` requires CP1.
- Other profiles mark CP1 as N/A unless upgraded by the rules above.
- `uses_existing_evidence_only=true` does not itself suppress CP1 if product baseline refresh is required.

### Human Gate Levels

Use three levels:

| Value | Meaning |
|---|---|
| `required` | Human approval is mandatory |
| `optional` | Auto path is allowed, but scope/authz/risk/open-question triggers upgrade to required |
| `none` | No human gate; reserved for narrow micro cases |

`process-lite` CP2 must be `optional`, not `false`. CP2 upgrades to `required` if any condition is true:

- `cr_type` is `product-scope`, `architecture` or `runtime`.
- `product_baseline_refresh_required=true`.
- `impact_surface` includes scope, use cases, requirements or product baseline.
- Scope/authz OPEN, LCQ or decision items remain unresolved.
- Authorization boundary is new or differs from parent/baseline.
- Existing evidence refs are incomplete for an existing-evidence closeout.
- User explicitly asks for scope review.

## Implementation Plan

### Step 0 - Immediate Compatibility Fixup

Purpose: remove current checker/profile drift before route-plan work begins.

Changes:

- Synchronize `meta_flow/checks/cr_tracking.py` gate profile validation with `gate_profiles.default_gate_profiles()["profiles"].keys()`.
- Keep `cr_kind` as deprecated compatibility only.
- Do not add new recommended `cr_kind` values. New classifications go through `cr_type`.
- Prevent `cr_kind` from being auto-filled with arbitrary `cr_type` values.
- Add tests proving `micro`, `docs-lite`, `process-lite`, `standard-lite`, `architecture-major` and `runtime-high-risk` are accepted gate profiles.

Deliverables:

- `meta_flow/checks/cr_tracking.py`

### Step 1 - CR-157+158 Combined Route Plan and N/A Semantics

Purpose: restore CR-aware routing and legal N/A checkpoint decisions as one coherent contract.

Changes:

- Add `meta_flow/policies/route_plan.py`.
- Add `meta-flow route plan` CLI entry.
- Normalize profile stages from `CPx-lite` strings to structured objects.
- Add `cr_trait` route facts to CR template and summary/index generation.

- Add checkpoint-level `N/A` to CP result decisions.
- Add validation rules:
  - `decision=N/A` requires route-plan/applicability reason.
  - `decision=WAIVED` requires waiver records.
  - `WAIVED` items continue to require `waiver_ref`.
- Update state-router in three places:
  - Stage progression reads `route_plan.stages`.
  - CP result synchronization reads `route_plan.checkpoint_applicability`.
  - Product-baseline routing is enforced during route-plan generation and remains a high-priority upgrade rule.
- N/A checkpoints do not generate, read or validate independent result JSON files.

### Step 3a - Silent Validation Mode

Purpose: reduce token leakage from large JSON validation.

Changes:

- Add `--mode silent|normal|verbose` to:
  - `meta-flow cp result-check`
  - `meta-flow event check`
  - CR/index checks where large payloads can leak
- Silent OK prints only status.
- Silent FAIL prints error summaries, not payload dumps.
- Default usage in low-token paths prefers silent.

Deliverables:

- `meta_flow/checks/cp_result.py`
- `meta_flow/state/event_ledger.py`

### Step 3b - Applicability Aggregate and Artifact Deduplication

- Keep the main CP result schema limited to CP0 through CP8.
- Add context/checkpoint ref-based deduplication for minimal/process-lite closeouts.
- Add human-gate launch replay from checkpoint instead of default persistent launch-message files.

Deliverables:

- `meta_flow/checks/cp_applicability.py` or equivalent

### Step 4 - Regression Guardrails

Purpose: prevent route-plan capability from drifting back into documentation-only behavior.

Required tests:

- runtime-high-risk CR cannot be pruned to process-lite.
- product-baseline refresh requires CP1/CP2 and blocks Story decomposition until CP2.
- architecture review requires CP3 standard/human gate.
- `CP2-lite` legacy input normalizes to CP2 + mode lite.
- checkpoint-level `N/A` is valid and distinct from `WAIVED`.
- state-router does not attempt to read result files for route-plan N/A CPs.
- dispatch_not_required is accepted only when route_plan supports it.
- `ALLOWED_GATE_PROFILES` remains synchronized with default gate profiles.

## Acceptance Criteria

- `meta-flow route plan` can preview deterministic route plans from `cr_type`, `cr_trait` and `gate_profile`.
- `process-lite + uses_existing_evidence_only=true` derives a CP0/CP2/CP8 route and marks CP3-CP7 N/A without per-CP N/A result files.
- `process-lite + has_new_implementation=true` keeps CP6/CP7 applicable.
- `has_new_implementation=true` derives CP7 unless an explicit verification waiver exists.
- `decision=N/A` is accepted at checkpoint level and does not require waiver records.
- `decision=WAIVED` requires waiver records and cannot be used as a synonym for N/A.
- state-router consumes `route_plan` in progression and CP result lookup.
- CP2 human gate uses `required|optional|none`, and process-lite CP2 can upgrade from optional to required.
- CP1 applicability follows gate profile and product-baseline refresh rules.
- `ALLOWED_GATE_PROFILES` cannot drift from default gate profiles.
- CR-156 fixture prevents recurrence of full CP3-CP8 over-processing for existing-evidence closeouts.
