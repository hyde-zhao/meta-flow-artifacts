# CR-046 Evidence integrity, replayability, and token telemetry governance

## 变更描述

修改 Meta Flow，使其从“主要证明 schema 能过”升级到“能证明时序可信、平台调用可证、当前 checker 可重放、成本可量化”。随后以 quant-lab CR-163 作为 append-only 历史证据迁移和验收试点，但不修改或重做 quant-lab lineage 业务实现。

## Scope

In scope:

- Gate temporal invariant 与条件式批准状态机。
- Dispatch 平台 receipt、attempt 生命周期、retry/supersession 和 terminal closure。
- Codex 自定义子 Agent 的强类型解析与证明链：区分 canonical role、task/thread 名称、requested profile、resolved profile 和 execution identity；配置存在、平台发现、显式 selector、平台 receipt 与实际 model/reasoning attestation 必须分层验证，`task_name`、prompt 角色声明或 ledger 自报不得冒充平台选择证据。
- 自定义 Agent 严格降级策略：required critical/debugger profile 在未发现、无显式 selector、receipt 缺失或 requested/resolved 不一致时 fail-closed；兼容 fallback 仅能在用户明确批准后标记为 degraded/unattested，且不得产生 `custom_agent_verified=true`。
- 规范性 Codex Subagent Platform Contract 附录：分开记录官方已验证能力、当前会话可调用 schema 和 CR-046 required extension；明确 spawn/profile discovery/request/receipt、followup/reuse、thread identity、fallback 与 acceptance fixture，禁止把期望 API 写成现有事实。
- Capability discovery 来源层级：平台 list/resolve capability receipt 才能产生 `PROFILE_DISCOVERED`；扫描 `.codex/agents/*.toml` 只产生 `CONFIG_VALIDATED` / candidate inventory，不能证明当前会话已发现。
- Thread runtime identity 与复用：初始 platform receipt 绑定的 resolved profile/model/effort/config hash 在线程内不可由 handoff/ledger/followup 改写；`followup_task` / resume / send_input 只能继承。profile 升级必须 new spawn 并生成新 receipt/lineage。
- CR-046 dogfooding 策略：以 session-observed 的诚实降级路径作为可保证基线；若 CP7 前平台 selector/discovery/receipt 已可用，则必须切换到自举后的新 producer 并 new-spawn `meta-qa-critical` 完成条件式 runtime-attested 验证。平台仍不可用时允许功能 CP7 `PASS_WITH_RISK`，但 custom-profile capability 只能标 `contract-ready/unverified`，CP8 最高 `READY_WITH_RISK`。
- CP result 的 check attempt、输入 artifact hash、supersedes 与最终 dispatch correlation。
- result/checkpoint/gate/state/ledger 的跨真相源一致性校验。
- delivered state finalization 与 workflow health 生成物存在性、当前 CR 归属检查。
- Read expansion 显式授权语义、CR attribution 与 scoped context slicing。
- 平台报告的 token usage telemetry；不可用时显式记录 unavailable，禁止以估算值冒充实测。
- Checker 版本、commit、schema/policy hash 与 as-executed/current-replay 双口径。
- Ledger compaction/restore 的语义保持契约：不得混淆 event、dispatch、attempt、run 标识，不得截断 terminal selection、correction chain 或 workflow-health ref。
- CP8 后 append-only correction lifecycle：versioned correction event schema、允许修正范围、author/reason/evidence/supersedes 与独立 audit trail。
- 机器生成的 provenance-bearing audit report：分别统计 event rows、attempts、threads、terminal outcomes 与 measured/proxy/unavailable token usage，禁止从 dispatch 行数推断 token 占比。
- quant-lab CR-163 的 append-only migration manifest、correction/supersession events 和 current-checker replay fixture。
- canonical JSON CR index 迁移并移除 legacy YAML 对 canonical checker 的干扰。

Out of scope:

- 修改 quant-lab lineage contract、recorder、producer、consumer 或 admission 业务代码。
- 追溯伪造历史平台签名或 token usage。
- 授权 credentials、runtime、production write、publish、交易或远端 repository publication。
- 把所有 Story QA 合并成单一 batch；Story 结论仍保持独立，只有共享回归可批量运行。

## 初始验收边界

1. chronology negative fixtures 100% rejected；合法条件式批准可完整重放。
2. 每个 execution attempt 有 terminal status；retry/supersession 可追踪。
3. final CP result 引用最终 terminal attempt，且 terminal outcome 与 CP decision 兼容。
4. 适用 CP result 的 input artifact hash 和 check attempt 覆盖率 100%。
5. delivered state 的 active refs 为 0；workflow health ref 目标存在且属于当前 CR。
6. deny-default read expansion 未授权事件为 0；授权、原因、CR attribution 可验证。
7. usage `measurement_status` 覆盖率 100%；measured 与 unavailable/estimated 严格区分。
8. replay report 同时记录 checker version/commit/schema-policy hash 和 as-executed/current-replay 结果。
9. compaction + restore 后 attempt/correction/health-ref 图与 compaction 前语义等价，负向 conflation fixture 100% rejected。
10. post-close correction event schema、允许范围、审计 trail 和 supersession closure 具备机器校验；非法历史改写 100% rejected。
11. audit report 由工具生成并携带 checker provenance/input hashes；event/attempt/thread/token measurement status 分栏且统计 fixture 100% 正确。
12. CR046 CP1/CP2 null provenance 被保留为 dogfooding negative fixture；新 strict profile 不得把它报告为 fully replayable。
13. 当前 meta-pm dispatch 证据等级显式为 `session-observed/repository-unverifiable`，直到存在 platform receipt。
14. quant-lab CR-163 current replay 目标为 23/23 PASS；历史事件不改写，只追加 correction/supersession/migration evidence。
15. quant-lab lineage 业务源码 diff 为 0。
16. 自定义 Agent 调度必须形成 `CONFIG_VALIDATED -> PROFILE_DISCOVERED -> DISPATCH_SUBMITTED -> RECEIPT_RECEIVED -> PROFILE_RESOLVED` 证明链；execution completion 与 profile/model attestation 分开判定。
17. 指定 profile 的 dispatch request 必须通过平台支持的 `agent_type` / `profile` 等显式 selector 传入；只有 requested/resolved profile、config hash、model 和 reasoning effort 与同一 dispatch/attempt receipt 全部一致时，才可标记 `platform-attested` / `custom_agent_verified=true`。
18. 以下负向 fixture 必须 100% 被 strict checker 拒绝：配置仅存在于磁盘但当前会话未发现、`task_name` 冒充 selector、ledger 自报但请求无 selector、requested/resolved profile 或 model 不一致、receipt 缺失/绑定错误 dispatch、config hash 过期。
19. CR-046 自身已发生的 Codex dispatch 在平台工具未暴露 custom-agent selector/receipt 时保留为 `session-observed/repository-unverifiable` dogfooding evidence；不得追溯补造 resolved profile、实际 model 或 receipt。
20. `CR046-CODEX-SUBAGENT-PLATFORM-CONTRACT.md` 必须区分 `officially-documented`、`session-observed` 与 `required-extension`，并对 spawn、discovery、receipt、followup/reuse 和 fallback 给出可机测 schema/fixture。
21. capability probe 只有平台签发的 list/resolve/dry-run receipt 可以产生 `PROFILE_DISCOVERED`；filesystem config scan 的最高状态固定为 `CONFIG_VALIDATED`。
22. 每个 thread 必须绑定不可变 `ThreadRuntimeIdentity`；followup/resume/send_input 的 requested profile/model/effort/config hash 与初始 receipt 不一致时必须 `NEW_SPAWN_REQUIRED` 或 `BLOCKED`，禁止 ledger mutation 升级。
23. profile requirement 必须显式为 `required|preferred`：required 缺 selector/receipt 时阻断；preferred 可在用户明确批准后 `degraded-unattested`，但不得产生 verified/model-applied 结论。
24. CR-046 dogfooding baseline 为 session-observed + fixture-verified contract/checker；平台 extension 不可用时 CP7/CP8 必须暴露 custom-profile runtime verification 未完成并最高 `PASS_WITH_RISK/READY_WITH_RISK`。若 extension 在 CP7 前可用，则必须使用 Story 2 新 producer new-spawn QA 并执行真实 receipt correlation。
