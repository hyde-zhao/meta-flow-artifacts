# CR-054 policy-route-execution 改名 case-op-execution + SKILL v2.0 定位刷新 + op-coverage-matrix v2.0 重建

## 变更描述

用户咨询"policy-route-execution 与 case-execution 功能是否重叠、可否合并"（2026-09-02）。事实核查结论：**两者不重叠，是 case-execution（批量用例编排 + 报告产出）→ policy-route-execution（op_id/args 翻译 + 单 op 执行/回滚原语）的分层单向依赖**（case_runner.py L37-57 sys.path 注入 import op_mapper，反向零依赖），不建议物理合并。真正的问题是 **policy-route-execution 命名与文档严重滞后**：SKILL.md 第一层映射只描述 8 个 policy-route op、修订记录停在 v1.4，而 `op_mapper.py`（3607 行）实际已是 **18 族 51 op 的通用执行层**（auth/policy-route/operation-log/object/interface/acl-policy/export-file/import-file/iplink/reboot/static-route/service-pool/tg/cli/session/neighbor/ha/sw3），docs/ptm-te/op-coverage-matrix.md 停在 v1.0（2026-07-13，21 mapped）。

用户决策（2026-09-02 结构化决策）：
1. **改名**：`policy-route-execution` → **`case-op-execution`**（消费 PC 用例 step、驱动 ptm-atomic op 执行/验证/回滚的用例原子操作执行层；与 case-execution「批量用例编排+报告」成对分工）；
2. **op-coverage-matrix.md 一并纳入本 CR 重建**（需 ptm-atomic list 实测当前全集）；
3. SKILL.md 同步 v2.0 定位刷新（18 族 51 op 总表 + 相邻对象边界理顺 + 真相源多族化）。

## 需求基线

用户原话要点："两个 skill 的功能是否是重叠的，是否可以合并" → 分析结论采纳 → "需要改名，但不是 op-execution，应该是 case-编排器，你给出几个候选名我再决策" → 结构化选择 **case-op-execution**；"滞后的 op-coverage-matrix.md 是否纳入本 CR 范围" → **一并纳入**。（2026-09-02）
