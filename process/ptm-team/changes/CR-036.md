### C. case_runner.py TG 端口生命周期（P0 · 基于真实环境验证制定）

#### 验证结论（2026-08-01 真实环境：DUT 10.113.55.171 + trex 10.113.55.175）

| 验证目标 | 方法 | 结果 |
|---|---|---|
| 1. acquire 幂等性 | 同 user_id 同端口重复 acquire-ports（force=False） | ✅ success，重复 acquire 不冲突 |
| 2. stop-stream 释放 owner | acquire -> start -> stop -> verify-ownership | ⚠️ **环境相关非确定行为**：8-1 验证 stop 后 owner 仍在（count=1），start 成功；但 7-31 exec-log 同 user_id stop 后 start `exit=47 must be acquired`（owner 丢失）。stop response 均为 `cleaned:true`，但 owner 行为不一致 |
| 3. 重新 acquire 恢复 owner | owner 丢失后重新 acquire-ports -> start | ✅ acquire success + start success |

**7-31 exec-log 真相**（run-20260731-173134-99c8d7）：
- [14] 01 的 tg_stop（`dev1-9126`）success，`cleaned:true`
- [15-19] 03 的 fw_config + tg_apply_template（中间无 tg_release）
- [20] 03 的 tg_start（同 `dev1-9126`）exit=47，stderr `port(s) [0]: must be acquired`

**根因认定**：owner 丢失是环境/状态相关的非确定行为（stop 释放或 trex 底层 session 占用，CR-035 static-only 验证未覆盖，RISK-CR035-RUNTIME-NA 在真实环境暴露）。

#### 方案决策：方案 A 补充（per-case 幂等 acquire，保留 CR-035 acquire-once）

| 维度 | 决策 |
|---|---|
| 与 CR-035 关系 | **补充**（非替代）。保留 acquire-once [4c] / config-once / release-once [6c] |
| 实现点 | `execute_steps` 检测每用例首个 `tg_*` op 前（非 dry_run），幂等调 `tg_acquire_ports`（`tg_run_ctx.tg_user_id` + `_resolve_tg_ports`） |
| 机制 | acquire 幂等：owner 在则无操作，丢失则恢复。防御 stop 释放/底层占用/超时等非确定 owner 丢失 |
| 与 config-once 交互 | acquire 在 config 前，保障 owner；config-once skip 不受影响 |
| 失败处理 | acquire 失败记 warning 不阻断（owner 可能已在）；start 失败仍按现有错误处理 |

**execute_steps 插入时序**（与 CR-035 config-once skip / tg_user_id 注入的相对顺序，LLD 必须明确）：

```
[用例开始] -> [per-case acquire：幂等 tg_acquire_ports（tg_run_ctx.tg_user_id + _resolve_tg_ports）]
  -> [config-once skip 判断（L1626，acquire 保障 owner 与 config skip 无关）]
  -> [tg_user_id 自动注入（L1658，后续 tg op 携带 --user-id 走 owned 模式）]
  -> [step 执行]
```

约束与层级：per-case acquire 是**用例级**（每用例首个 `tg_*` op 触发一次），与 config-once skip（**step 级**，每个 `tg_config_interface` step 判断）是不同循环层级，时序图仅对"首个 tg op 恰为 tg_config_interface"成立。**状态载体**：per-case acquire 用 execute_steps 局部标志 `per_case_acquired`（每用例重置，不放 tg_run_ctx 跨用例），检测 `op_id in TG_OPS_NEED_USER_ID and not per_case_acquired` 时触发，与 CR-035 run 级 `tg_run_ctx` 状态隔离。acquire 依赖 `tg_run_ctx.tg_user_id`（main 已生成，execute_steps 可直接取）。acquire 失败记 warning 不阻断（owner 可能已在），但 start 失败时错误信息应关联 acquire 状态（如 `owner 可能丢失，per-case acquire 返回 <status>`），避免 owner 丢失 + acquire 失败的连锁错误难诊断。

**不确定性**：当前环境（8-1）无法稳定复现 stop 释放 owner，方案 A 基于幂等性防御逻辑。需 7-31 类似环境批量执行回归验证（关联 CR-035-FU-01 runtime 端到端验证）。

**保留 [4c]/[6c] 的冗余评估**（P3，CP5 LLD 层面）：per-case acquire 幂等已覆盖 owner 保障，[4c] acquire-once / [6c] release-once 是否可简化（减少 N+1 次 acquire 调用）由 CP5 LLD 评估；本 CR 维持"补充非替代"决策，不废弃 [4c]/[6c]。
